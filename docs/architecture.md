# Prutet — Architecture (living doc)

This file evolves with each phase. Phase-1 entries describe what is shipped
*today*; later sections are sketches that will be filled in as the relevant
code lands.

## 1. Threat model

| Adversary                     | What they must not learn          | Mitigation                                                 |
| ----------------------------- | --------------------------------- | ---------------------------------------------------------- |
| Network observer              | Evidence content                  | Client-side AES-GCM with Argon2id-derived key.             |
| Relay operator                | Evidence content + identity       | Relay only sees opaque ciphertext; no auth, no PII fields. |
| On-chain observer             | Real-world identity of an anchorer| Anchoring keypair is random and never linked off-chain.    |
| Lost / stolen device          | Past evidence                     | Encryption key is derived from a passcode, never stored.   |
| Coerced disclosure of address | Past evidence beyond what's shown | "Burn" instruction destroys the key; new keys are unlinkable. |

## 2. On-chain layer

### `evidence_anchor`
- **PDA seeds:** `[b"anchor", signer, nonce_le]`. The nonce makes per-user
  anchors enumerable by the user without requiring an indexer.
- **Account fields:** `owner, hash, location_commitment, timestamp, slot, nonce, revoked, bump`.
- **No PII.** The "owner" field is just the random Solana keypair — there is
  no email, phone, or mapping to one.
- **`revoke_anchor`** is deliberately weak: it only flips a public flag, since
  true erasure must come from key destruction off-chain. Strong erasure for
  on-chain *content* would require storing nothing identifiable in the first
  place, which is exactly what we do.

### `zk_verifier`
- Implements a generic Groth16 verifier on top of Solana's `alt_bn128_*`
  syscalls. The VK is a single PDA per `(authority)` so multiple circuits can
  coexist by deploying multiple VK PDAs.
- Supports up to `MAX_PUBLIC_INPUTS = 16` public inputs (more than enough for
  the Prutet circuit, which exposes `hash_lo, hash_hi, slot_min, slot_max,
  location_commitment`).
- Verifying-key layout matches snarkjs / circom (G1 = 64 B big-endian x||y,
  G2 = 128 B). Phase 2's keygen script will export VK bytes in this layout.

## 3. Identity & erasure

The user identity is a Solana keypair generated locally on first launch and
encrypted with the device passcode (Argon2id → AES-GCM key wrapping). It is
never sent to the relay or anywhere else. Burning = securely deleting that
keypair (and any wrap-key material) from local storage. Once destroyed, the
on-chain anchors become unlinkable — they reference a public key that no
party can prove they ever held.

## 4. Phase 2 — ZK selective disclosure (shipped)

Circuit `circuits/evidence_zk.circom`:

- Public inputs: `slot_min`, `slot_max`, `location_commitment`, `nullifier`.
- Private witnesses: `content_hash_lo/hi` (SHA-256 split into two 128-bit
  limbs), `slot`, `lat`, `lon`, `loc_salt`.
- Constraints:
  1. `nullifier == Poseidon(content_hash_lo, content_hash_hi)`
  2. `slot_min ≤ slot ≤ slot_max` via 64-bit comparators
  3. `location_commitment == Poseidon(lat, lon, loc_salt)`

The full SHA-256 binding (computing SHA-256 *inside* circom) is intentionally
deferred — it would add ~50k constraints and is not required for the Phase-2
demonstration. The Poseidon-nullifier indirection still gives a binding
handle the verifier can compare against an off-chain index.

Build pipeline (`circuits/scripts/build.sh`):

1. powers-of-tau `2^14` ceremony (single contributor, dev-only).
2. `circom --r1cs --wasm --sym`.
3. `snarkjs groth16 setup` → contribute → export verifying key.
4. `export_vk_solana.ts` repacks the VK into Ethereum-style byte order so it
   loads directly into the `zk_verifier` PDA (`alpha=64B, β/γ/δ=128B, IC[i]=64B`).

Proofs are generated by `circuits/scripts/prove.ts::generateSolanaProof()`.
The same module is consumed by `tests/zk_verifier_e2e.ts` (Node) and will be
consumed by a Web Worker in the Phase-4 frontend.

## 6. Phase 3 — Relay (shipped)

`relay/` is an Express + TypeScript service with two endpoints:

| Endpoint                       | Purpose                                                |
| ------------------------------ | ------------------------------------------------------ |
| `POST /v1/pin`, `/v1/unpin`    | Forward an opaque (already-encrypted) blob to a pinning provider. |
| `POST /v1/emergency/dispatch`  | Fan-out a pre-encrypted alert via SMS (Twilio) or SMTP. |

Hardening:

- `helmet` with deny-all CSP (the API never serves HTML).
- CORS allowlist via `CORS_ORIGINS`.
- `express-rate-limit` per route family (pin / emergency are independent budgets).
- `pino` logging with explicit redact paths for recipient addresses, ciphertexts, and auth headers.
- Recipient `to` is hashed (`sha256`, 16-hex prefix) in every response and log.
- `zod` schema validation at every boundary; bad config refuses to boot.

Pinning provider is pluggable: `local` (Kubo HTTP API), `web3storage`,
`pinata`, or `noop` (used by the in-process test suite). The relay holds no
keys and persists nothing.
